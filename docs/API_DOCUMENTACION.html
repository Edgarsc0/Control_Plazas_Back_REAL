Fundamentos

Convenciones del contrato

Todo lo que aplica a cualquier endpoint. Las fichas individuales sólo documentan lo que se desvía de esto.

Construcción de la URL

El cliente nunca escribe la URL completa: apiFetch(endpoint) (src/lib/fetch-interceptor.js) antepone ${NEXT_PUBLIC_API_URL}/api. En esta documentación las rutas se escriben sin ese prefijo, exactamente como se pasan a apiFetch. 

apiFetch("/plantilla/cuadro_vacancia/")
  → GET https://<host>/api/plantilla/cuadro_vacancia/
Barra final obligatoria. Django corre con APPEND_SLASH; una ruta sin / final responde 301 hacia la versión con barra. El único caso vigente en el front es VacantesService.getVacantesPorNivelResumen(), que llama /plantilla/estatus_nomina_por_nivel/resumen sin barra y paga un redirect extra en cada carga.

Autenticación

El backend acepta tres esquemas (DEFAULT_AUTHENTICATION_CLASSES): TokenAuthentication, SessionAuthentication y BasicAuthentication. El frontend usa exclusivamente el primero: guarda el token en la cookie auth_token (7 días, sameSite=lax) y apiFetch lo inyecta como header. 

Authorization: Token 9c8f1e2a4b6d0f3c5a7e9b1d3f5a7c9e1b3d5f70
Content-Type: application/json

Cualquier respuesta 401 hace que el interceptor borre la cookie y redirija a /login. El único endpoint que no puede mandar header es el SSE de celdas: EventSource no permite headers, así que ahí el token viaja como query param.

Autorización

Además de IsAuthenticated, todas las vistas pasan por authentication.permissions.HasModulePermission. Cada vista declara opcionalmente:

AtributoAplica aSemántica
view_permissionGET, HEAD, OPTIONSPermiso requerido para leer. Si es lista/tupla, basta tener al menos uno.
edit_permissionPOST, PUT, PATCH, DELETEPermiso para escribir. Si falta, cae a view_permission.
action_permissions@action de ViewSetsMapa {nombre_action: permiso}. Gana sobre los dos anteriores.

Una vista sin ninguno de esos atributos sólo exige estar autenticado. Los superusuarios siempre pasan (comportamiento nativo de user.has_perm). El rol de whitelist llamado superadmin activa is_superuser/is_staff automáticamente al iniciar sesión o al reasignar el rol.

Serialización y respuestas

  • Renderer: ORJSONRenderer (orjson) en todas las respuestas DRF. Los Decimal se serializan como string; cualquier tipo no soportado cae a str(obj) en vez de reventar.
  • Fechas: los DateField/DateTimeField salen en ISO-8601. Ojo: la mayoría de las columnas de ZAFIRO son CharField con la fecha ya escrita como texto YYYY-MM-DD, no tipos de fecha reales.
  • Listas grandes: /plantilla/plantilla_1800_plazas_list/ evita DRF por completo y sirve bytes JSON precocinados con orjson_response.
  • Excel: los endpoints de exportación devuelven application/vnd.openxmlformats-officedocument.spreadsheetml.sheet con Content-Disposition: attachment. El cliente debe usar .blob(), no .json().

Forma de los errores

El backend no unificó la llave de error. Conviven tres formas y el cliente debe tolerar las tres:

FormaOrigenEjemplo
{"error": "..."}APIView escritas a mano{"error": "Parámetro 'posicion' es requerido."}
{"detail": "..."}DRF nativo y vistas nuevas{"detail": "posicion y columna son requeridos."}
{"campo": ["..."]}ModelSerializer con validación{"escala": ["Este campo es requerido."]}
Los 500 de plantilla nunca filtran el traceback: se registra con logger.exception y se responde {"error": "Error interno del servidor"}.

Caché

El backend usa el cache de Django respaldado por el mismo Redis de Celery. Cada ficha indica su TTL. Los invalidadores relevantes:

  • La tarea Celery importar_zafiro (cada 30 min) trunca y recarga EMPLEADOS_COMPLETOS_SIG, MOV_POS, BAJAS_SIG y barre las llaves de caché derivadas.
  • POST/DELETE /plantilla/empleados_completos_sig/override/ invalida empleados_completos_activos_detalle, active_employees_filtered y todas las variantes filtradas por patrón en Redis.
  • PATCH /plantilla/plantilla_1800_plazas_list/ invalida plantilla_1800_list_json.

Motor de filtros de tabla

Contrato compartido por mov_pos_detalle, movimientos-personal, mov_pos_alineacion y el export Excel de posiciones. Se documenta una vez aquí; las fichas sólo listan las columnas válidas de cada tabla.

1 · Filtros dinámicos de columna

Implementado en apply_dynamic_column_filters(). Cualquier campo real del modelo se convierte en query param. Las columnas de texto se filtran sobre TRIM(campo) (anotación trimmed_<campo>), que es lo que aprovechan los índices funcionales de MySQL.

SintaxisEfectoEjemplo
?campo=valorTexto → icontains. No-texto → igualdad exacta.?motivo=BAJA
?campo=v1,v2,v3Selección múltiple → __in.?estado_psn=A,I
?campo__in=v1,v2__in explícito.?nivel__in=A212,D312
?campo__istartswith=xSufijos de lookup de Django: icontains, istartswith, iendswith, iexact, in.?nombre_puesto__istartswith=DIRE
?exclude__campo=v1,v2Negación: se aplica .exclude() en vez de .filter().?exclude__motivo=ALTA
__EMPTY__Sentinel para seleccionar «(Vacío)». Se traduce a "" y además cubre NULL real (porque TRIM(NULL) es NULL en MySQL).?ubicacion=__EMPTY__,MEX

Parámetros que nunca se interpretan como columna (FILTER_SKIP_PARAMS): distinct_field, distinct_search, page, page_size, search, is_latest, no_pagination, sort_by, sort_order, oficio, nivel, advanced_filters.

2 · Filtros avanzados

Parámetro ?advanced_filters= con un array JSON URL-encoded (máximo 20 condiciones; el resto se descarta). Cada condición combina con el acumulado de las anteriores según su logic. 

[
  { "column": "unidad_adva", "condition": "equals",   "compareType": "valor",  "value": "700", "logic": "AND" },
  { "column": "fecha_captura","condition": "after",    "compareType": "valor",  "value": "2026-01-01", "logic": "AND" },
  { "column": "f_efva",       "condition": "equals",   "compareType": "campo",  "compareColumn": "fecha_captura", "logic": "OR" }
]
CampoTipoValores
columnstringNombre del campo del modelo, o una columna calculada si la vista aporta resolver.
conditionstringTexto: contains, not_contains, starts_with, not_starts_with, ends_with, not_ends_with, equals, not_equals. Fecha: before, after, before_or_equal, after_or_equal, equals, not_equals.
compareTypestring"valor" (default) compara contra value; "campo" compara contra otra columna vía compareColumn.
valuestringValor a comparar. Vacío o nulo ⇒ la condición se ignora por completo.
compareColumnstringSólo con compareType: "campo". Debe ser campo real del modelo.
logicstring"AND" (default) u "OR": cómo se une con el acumulado previo.
Semántica NULL. En SQL NOT (NULL LIKE …) es NULL, no TRUE. Las condiciones negativas de texto (not_contains, not_equals, …) añaden explícitamente OR campo IS NULL para que las filas vacías sí aparezcan. Lo mismo para not_equals sobre fechas.
Fechas guardadas como texto. fh_ult_actz guarda YYYY-MM-DD-HH.MM.SS.ffffff como CharField: se compara por SUBSTR(campo,1,10). Los DateTimeField reales se truncan con un offset calculado en Python (zoneinfo) porque el MySQL de este entorno no tiene cargadas las tablas mysql.time_zone_* y CONVERT_TZ devolvería NULL para todas las filas.

3 · Valores distintos para el dropdown de columna

?distinct_field=<campo> cambia por completo la forma de la respuesta: en vez de filas, devuelve el conteo de cada valor único, ya afectado por todos los demás filtros activos (búsqueda, filtros de columna y filtros avanzados). ?distinct_search= filtra ese listado. 

GET /plantilla/mov_pos_detalle/?distinct_field=motivo&distinct_search=BAJ

[
  { "value": "BAJA DEFINITIVA", "count": 412 },
  { "value": "BAJA POR DEFUNCION", "count": 7 }
]

Sobre columnas de fecha (DateTimeField) el distinct_search compara contra la fecha truncada en UTC, no contra el texto: mandar 2026-05-14 funciona aunque la hora almacenada no sea medianoche.

Secuencia completa cuando el código es válido y no expiró:

  1. Marca el VerificationCode como is_used = True (un solo uso).
  2. User.objects.get_or_create(username=email, email=email).
  3. Sincroniza is_staff/is_superuser en ambos sentidos según si el rol de whitelist se llama superadmin — activa y también revoca, para que un cambio de rol no deje el flag pegado.

  6. django.contrib.auth.login() (crea sesión) y Token.objects.get_or_create() (token para la API).
El token DRF no expira ni rota: get_or_create devuelve siempre el mismo. Lo que caduca a los 7 días es la cookie del navegador.

Ambas acciones son idénticas salvo la partida presupuestal. Cuentan las plazas ocupadas (Estado Nómina <> ' ') de posiciones activas, agrupadas por Código Presupuestal + Escala + Nivel, y las resuelven contra catalogo_plazas para alimentar el simulador con una precarga realista.

Diferencia entre las dos. La consulta de permanentes excluye las posiciones que empiezan con 103L; la de eventuales no lo hace (aunque el conteo de totales por nivel sí las excluye en ambos casos).

Algoritmo de cruce

  1. Match directo por (codigo, nivel) contra catalogo_plazas.
  2. Si no hay match, se sustituyen los 2 primeros caracteres del código presupuestal por "EV" y se reintenta (el catálogo usa códigos EV* para todas las plazas).
  3. Si quedan varios candidatos, se desempata por zona == escala.
  4. Si no queda exactamente uno, el grupo va a sin_match y no se cuenta.
